Native iOS · Health & Nutrition

IGNITE

A native iOS health and nutrition tracker that brings food logging, activity, hydration, workouts, body weight, and long-term progress into one system.

Built with SwiftUI, Core Data, and HealthKit around a local-first architecture, with selective remote food discovery through Supabase and OpenFoodFacts.

Product idea

One place for the data that usually lives everywhere.

Health data is often fragmented across food trackers, workout apps, Apple Health, notes, and separate progress tools.

IGNITE was built around a simpler idea: bring the signals that matter day to day into one coherent system.

Nutrition, activity, hydration, workouts, supplements, body weight, and goals are connected through a single interface, while historical data turns daily tracking into something that can actually show progress over time.

[003]

Data boundary

Built local-first

IGNITE keeps the core tracking experience independent from the network.

Nutrition logs, meals, hydration, supplements, body weight, goals, and historical progress are persisted locally with Core Data, so everyday interaction does not depend on a remote backend.

Remote services are introduced only where they add value, primarily food discovery, barcode lookup, and subscription handling.

This keeps the core experience fast and resilient while still allowing the food catalog to grow beyond what ships with the app.

[004]

Repository flow

Food discovery without a single point of failure

Food lookup in IGNITE uses a hybrid data pipeline rather than relying on one source.

When a user searches for a food or scans a barcode, the app can resolve data through local Core Data, Supabase, and OpenFoodFacts.

Remote results are normalized, deduplicated, and persisted locally when useful, allowing the catalog to expand while keeping frequently accessed data close to the device.

  1. 01

    Local first

    Previously available foods are resolved directly from Core Data for fast access and offline reuse.

  2. 02

    Shared database

    Supabase extends the catalog with remotely available food records and user-contributed entries.

  3. 03

    Public fallback

    OpenFoodFacts provides an additional source for food and barcode discovery when a suitable match is unavailable elsewhere.

  4. 04

    Persist and reuse

    Useful remote results can be stored locally, reducing unnecessary requests during future lookups.

Native capture

Scan. Resolve. Log.

Barcode scanning is implemented natively with AVFoundation and connected directly to the food lookup pipeline.

A scanned code is not treated as an isolated feature. It enters the same repository layer used by food search, allowing IGNITE to check existing local data before reaching remote sources.

Once resolved, the food can move directly into the normal logging flow.

Platform integration

Connected to Apple Health

IGNITE integrates with HealthKit so activity and health data can move between the app and the wider iOS ecosystem.

Steps, active calories, body weight, and workouts can be read from Apple Health and incorporated into IGNITE's daily tracking and progress views.

Nutrition, hydration, weight, and workout data can also be written back to HealthKit, allowing IGNITE to contribute to the user's existing health record rather than keeping everything isolated inside the application.

HealthKit access is handled through dedicated services, keeping system-level health operations separate from the interface and other application logic.

Shared targets

Goals that connect the system

Onboarding establishes the targets used throughout IGNITE rather than simply collecting profile information.

Using body data and weight-change objectives, the app generates recommended calorie, macro, hydration, step, active-calorie, and body-weight targets.

Those values then become part of the daily tracking experience and progress system.

Calorie calculations use established metabolic formulas including Mifflin–St Jeor as part of the goal-generation logic.

The result is one set of targets shared across the application rather than independent goals configured inside every tracker.

Application architecture

Built as an application, not a collection of screens

The interface sits on top of separate view-model, repository, persistence, and service layers.

Views remain focused on presentation while repositories coordinate application data and dedicated services handle external systems such as HealthKit, StoreKit, and remote food sources.

Dependencies are assembled centrally through the application environment, making individual parts of the system easier to isolate, replace, and test.

[010]

Concurrency & resilience

Designed for asynchronous data

IGNITE has to work with several systems that operate independently: local persistence, network APIs, Apple Health, purchases, and background updates.

Swift concurrency is used across these boundaries so remote discovery and system integrations do not block the interface.

The architecture also allows network failures to remain localized. Losing access to a remote food source, for example, does not make the rest of the tracking system unavailable.

Persistence

More than the default database

As IGNITE evolved, its persistent data model evolved with it.

Core Data stores the application's structured tracking information across food, meals, supplements, hydration, weight, goals, and related records.

Persistence migrations allow the model to change without treating existing user data as disposable.

That makes the database part of the application architecture rather than simply somewhere to save values between launches.

Entitlements

Subscription infrastructure with StoreKit 2

Premium access is handled through StoreKit 2 rather than custom payment infrastructure.

IGNITE includes product loading, verified transaction handling, entitlement state, purchase restoration, transaction updates, and centralized feature gating.

Keeping entitlement logic separate from individual screens allows premium state to be managed consistently throughout the application.

Localization

Built for more than one language

IGNITE supports English, German, Spanish, and French, with language selection available inside the application.

Locale handling is centralized so interface language can be switched without tying individual views directly to localization logic.

This required treating text expansion, translated labels, and localized navigation as part of the interface rather than something added after the product was finished.

XCTest

Tested below the interface

The parts of IGNITE that carry the most application logic are also the parts that are tested independently of the UI.

XCTest coverage includes Core Data repositories, hybrid food discovery, barcode fallback behavior, caching, pagination, remote failure handling, deduplication, translation mapping, and view-model behavior.

In-memory Core Data stores and test doubles allow persistence and service behavior to be exercised without depending on production data or live external services.

The goal was not to test whether a button exists. It was to test whether the systems behind it behave correctly when data, state, or network conditions change.

Implementation rationale

Selected engineering decisions

01Local-first persistence
The core tracking experience does not require a permanent backend connection.
02Repository-based data access
Views do not need to know whether information originated from Core Data, Supabase, or OpenFoodFacts.
03Native platform integrations
HealthKit, StoreKit 2, AVFoundation, and Swift Charts are used directly where they fit the product.
04Selective networking
Remote services expand specific capabilities instead of owning the entire application.
05Reusable service boundaries
External systems and persistence logic remain separated from presentation code.
06Graceful fallback
Remote failures do not remove access to locally available tracking functionality.

Reflection

What I learned building IGNITE

IGNITE started as a tracking interface and gradually became an exercise in designing a system where multiple sources of truth have to coexist.

Local application data, Apple Health, public food information, shared remote records, purchase entitlements, and user preferences all behave differently.

The central challenge became deciding where each piece of data should live, which system should own it, and what should happen when another system is unavailable.

That changed how I approached the project.

Instead of adding every feature directly to the interface, I began treating persistence, networking, platform integrations, and state management as separate boundaries.

The result is a project that taught me considerably more about building maintainable software than simply building another set of iOS screens.

[018]

Result

One system.
Multiple signals.

IGNITE brings nutrition, activity, hydration, workouts, body weight, supplements, and progress together without requiring every part of the application to depend on the same data source.

It is the project where I moved from thinking primarily about screens to thinking about the systems behind them.
