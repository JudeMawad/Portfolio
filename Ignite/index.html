[002] Project / IGNITE

IGNITE

IGNITE is an iOS app I built to track food, workouts, activity, water, supplements, weight, and progress in one place.

I built it in Swift and SwiftUI, using Core Data, HealthKit, Supabase, and OpenFoodFacts for the main data flows.

[002]

The idea

Why I built IGNITE

The things I wanted to check every day were spread across nutrition apps, Apple Health, workout apps, and notes.

I built IGNITE so I could keep that information in one place. Food, workouts, water, supplements, weight, activity, and goals all feed into the same daily view and progress history.

[003]

On-device data

Most of the app works locally

Most of the data entered in IGNITE, including meals, water, supplements, weight, goals, and progress, is stored locally with Core Data.

The app only needs the internet for things such as food lookups, subscriptions, and other external services.

Existing logs and progress still work when there is no network connection.

[004]

Food search

One search flow for food

Text searches and barcode scans both use the same lookup.

IGNITE first checks foods already stored on the device. If there is no useful match, it checks Supabase and then OpenFoodFacts. Before showing or saving results, the data is cleaned up and duplicates are removed.

[005]

Barcode scanning

Scan instead of typing

I use AVFoundation to read barcodes with the iPhone camera.

Once a barcode is detected, it goes through the same food lookup as a text search. When it finds a match, the food can be logged and kept for later.

[006]

Apple Health

Connecting IGNITE to Apple Health

IGNITE reads steps, active calories, weight, and workouts from Apple Health.

It can also write supported nutrition, hydration, weight, and workout data back to HealthKit.

HealthKit code lives in dedicated services rather than SwiftUI views. This keeps permissions, queries, writes, observers, and background updates in one place.

Progress

Looking beyond one day

I use Swift Charts to turn daily tracking data into longer-term views for nutrition, activity, water, and weight.

Different time ranges make it easier to see changes that are hard to notice from one day alone.

[008]

Goals

Goals stay consistent across the app

During onboarding, IGNITE uses profile information and a weight goal to estimate calorie and macro targets with the Mifflin–St Jeor equation.

The app also sets up goals for water, steps, active calories, and body weight.

Those same values are used throughout the daily trackers and progress views, instead of being configured separately on each screen.

[009]

Architecture

How I split the app up

SwiftUI views handle the interface, while view models keep track of screen state and UI logic.

Repositories handle stored and remote data. Services handle things such as HealthKit, StoreKit 2, networking, and other system APIs.

I create the main dependencies in one place and pass them to the parts of the app that need them.

[010]

Async work

Doing background work without blocking the UI

I use Swift concurrency for network requests, HealthKit reads and writes, StoreKit purchases, and other work that should not block the interface.

The UI can keep responding while that work runs, then update when the result is ready.

If a remote food service is unavailable, saved meals, tracking, and progress still work locally.

Keeping data between launches

I use Core Data for foods, meals, supplements, water, weight, goals, and the other records IGNITE needs to keep.

As the data model changed, I added migrations so updates could keep existing user data instead of starting over.

Localization

Supporting four languages

I added English, German, Spanish, and French to IGNITE.

Language selection and locale handling are managed in one place.

It also forced me to test the layout with longer translations, because labels and navigation text do not take up the same space in every language.

Testing

Testing more than the screens

I mainly use XCTest for the parts of the app where mistakes are easy to miss in the interface.

Tests cover Core Data repositories, food-search fallbacks, caching, pagination, duplicate handling, network failures, translations, and view models.

For those tests, I use in-memory Core Data stores and test services so they do not depend on real user data or live APIs.

Reflection

What building IGNITE taught me

IGNITE started much smaller than it is now. As I added HealthKit, remote food data, subscriptions, and more local data, the hard part stopped being any single feature and became how all of them worked together.

I had to think about where each piece of data came from, where it should live, and what should happen when one of those sources was unavailable.

That is what pushed me to separate the SwiftUI views from storage, networking, and Apple framework integrations instead of letting those responsibilities pile up in the UI.

If I built it again, I would think about those boundaries earlier. IGNITE taught me how quickly structure starts to matter once a small app keeps growing.
