IGNITE

Project overview

I designed and developed IGNITE as a native iOS application.

IGNITE brings nutrition logging, hydration, workouts, supplements, activity, body metrics, and historical progress into one application. I built it to keep those related records in one place while making on-device storage the default for personal tracking data.

[002]

Application structure

A day-based dashboard is the primary working screen.

The dashboard displays calorie and macronutrient totals, water, meals, workouts, supplements, steps, and active energy for the current day. It is also the starting point for adding and updating daily records.

[003]

Features implemented

Four connected parts of the application.

01 / Daily dashboard

Current-day tracking in one view.

The main view displays calories, protein, carbohydrates, fat, water, meals, workouts, supplements, steps, and active energy. Users can review the day and start most logging actions from this screen.

02 / Food entry

Food search, portions, and custom entries.

Users can search public food data by barcode or name through OpenFoodFacts, review nutrition and portion information, set an amount, or create a custom food. Foods deliberately submitted to the shared library are stored in Supabase.

03 / History

Historical nutrition and body metrics.

Locally stored records are presented in 7-day, 30-day, and 365-day views for calories, protein, macronutrients, weight, and other progress data.

04 / Health & training

Workouts, supplements, and HealthKit context.

Workouts and supplements are stored with daily tracking data. With permission, IGNITE reads steps, active energy, weight, height, biological sex, and age from HealthKit. HealthKit writing remains disabled unless the user explicitly enables it.

Storage policy

On-device storage is the default.

Core Data stores nutrition, hydration, workout, supplement, and progress records locally. UserDefaults stores profile information and settings. Network requests occur only for requested OpenFoodFacts lookups and foods deliberately submitted to the Supabase community library. The app has no ads or analytics SDKs.

  • Core Data / Local
  • HealthKit / Permissioned
  • OpenFoodFacts / On demand
  • Supabase / Submitted foods

[005]

Implementation stack

A native Swift and SwiftUI application.

I designed and implemented IGNITE in Swift and SwiftUI. Core Data persists tracking and progress records, UserDefaults stores preferences, and HealthKit supplies permissioned health metrics. OpenFoodFacts handles requested food lookup, while Supabase stores food entries submitted to the shared library.

Data flow

Local application state with two network paths.

The SwiftUI interface works with on-device application data. Core Data holds tracking records, UserDefaults holds profile information and settings, and HealthKit remains behind Apple’s permission system. A barcode or name query reaches OpenFoodFacts only when requested; a Supabase write occurs only when a food is submitted to the shared library.

Engineering decisions

Three engineering decisions in the implementation.

01 / Storage boundary

Keep personal tracking off the backend.

Nutrition, hydration, workout, supplement, progress, profile, and settings data remain on the device.

Implementation Core Data stores tracking records and UserDefaults stores preferences; neither OpenFoodFacts nor Supabase is part of that persistence path.

02 / Health data

Keep HealthKit access permission-controlled.

IGNITE requests the health metrics used by the product: steps, active energy, weight, height, biological sex, and age.

Implementation Reads remain behind Apple’s permission system, and writing stays disabled unless the user explicitly enables it.

03 / External services

Limit food requests to the data each service needs.

OpenFoodFacts receives only a requested barcode or food name. Supabase receives only foods deliberately submitted to the community library.

Implementation Health data, profile information, account identifiers, and device identifiers are excluded from both network paths.

Project result

A native iOS product designed and built end to end.

I designed the product and implemented the iOS application in Swift and SwiftUI. The main lesson was that persistence, permission boundaries, external data, and App Store distribution have to be designed alongside the interface—not treated as separate finishing tasks.
